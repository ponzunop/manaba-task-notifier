# チーム12 発表・質疑応答・コード説明ガイド (`PRESENTATION_GUIDE.md`)

授業でのデモ発表・コードレビュー・質疑応答において、**4人（大友・蘆川・宮川・川邉）それぞれが自分の担当箇所をそのまま説明できる台本と技術的アピールポイント**をまとめています。

---

## 1. 全体導入（発表冒頭 30秒 / 大友または代表者）

> 「チーム12が開発した『manaba 課題通知システム』は、課題の提出忘れを防ぐ学生向けの Web アプリです。  
> ポイントは **manaba 本体にスクレイピング等で直接干渉せず、Google OAuth 2.0 と Gmail に届く通知メールを解析して課題を自動取得する**点です。取得した課題は締切順に一覧表示でき、設定した複数の通知タイミング（例：24時間前・5時間前・1時間前）に Web Push でリマインドします。提出後はワンクリックで通知を止められ、送信に失敗した通知も履歴画面から再試行できます。」

---

## 2. メンバー別 発表台本・アピールポイント

### A: 連携・ログイン・共通基盤担当（大友）

#### 発表台本（約1分）
1. **共通基盤（DB設計・Entity/Repository）**:
   「私はプロジェクトの土台となる共通 Entity 4テーブル（`users`, `tasks`, `notification_settings`, `notification_logs`）と Repository、そしてログイン・Gmail 課題取得を担当しました。」
2. **認証・セッション管理（`AuthController.java` / `login.html`）**:
   「セキュリティ上、システム側では Google や manaba のパスワードを保持せず、OAuth 2.0 認可フロー（`GET /auth/google` → `/auth/callback`）とセッション Cookie（`user_id`）で認証状態を維持します。すでにログイン済みであれば `/` や `/login` にアクセスしても自動で `/tasks` に遷移します。」
3. **メール解析とデータ保護（`TaskFetchService.java`）**:
   「`parseManabaEmail()` では正規表現でメール件名・本文から『科目名・課題名・締切日時』を抽出します。特に工夫した点として、**再同期時に既存課題が見つかっても、ユーザーが設定した『提出済み（`submitted=true`）』フラグは上書きせず、締切日時の変更のみ反映する**ようにしました。また、メンテナンス通知などの対象外メールは例外で落とさず安全にスキップします。」

#### コード説明の注目箇所
- `Task.java` / `NotificationSetting.java`: `isSubmitted()` と `getSubmitted()`、`isEnabled()` と `getEnabled()` の両方を実装し、Thymeleaf と他担当の Java コード双方から一貫してアクセスできるようにしている。
- `push-client.js` / `sw.js`: Service Worker 登録と `Notification.requestPermission()` を行い、`/auth/push-subscribe` へ購読情報を送信する。

---

### B: 課題一覧・提出済み管理担当（蘆川）

#### 発表台本（約1分）
1. **課題一覧と締切順表示（`TaskController.java` / `tasks.html`）**:
   「私は課題一覧と提出状態管理を担当しました。`GET /tasks` ではログイン中のユーザーの課題を `deadline` の昇順、つまり締め切りが近い順に取得し、上部サマリーカード（全課題・未提出・締切間近・提出済み）と一覧テーブルに表示します。」
2. **視覚的な緊急度・絞り込み**:
   「`TaskView` で現在時刻との差分を計算し、期限超過は赤、24時間以内はオレンジの『締切間近』バッジと残り時間（`あと ○時間 ○分`）を表示して一目で優先度が分かるようにしています。科目フィルタやキーワード検索にも対応しています。」
3. **提出済み更新と通知連動（`POST /tasks/{taskId}/submit`）**:
   「課題を提出したあとに『提出済みにする』ボタンを押すと DB の `is_submitted` が `true` に更新され、川邉さんの通知スケジューラが自動で対象外にして以後の通知を止めます。なお更新時には必ず `task.getUserId()` とセッションの `user_id` を照合し、他人の課題を変更できないようにしています。」

#### コード説明の注目箇所
- 不正 ID・他ユーザー操作・DB エラー時は詳細設計書通りに「`課題の状態更新に失敗しました`」を `RedirectAttributes` で表示。
- デモ用に「未提出に戻す（`/unsubmit`）」と「＋ 課題を手動追加（`/tasks/create`）」を備え、実演で自由に締切間近の課題を作ってテストできる。

### C: 通知設定担当（宮川）

#### 発表台本（約1分）
1. **機能概要（`SettingController.java` / `settings.html`）**:
   「私は『いつ通知するか』と『どの科目を通知するか』を決める通知設定画面を担当しました。`GET /settings` ではユーザーの既存設定に加え、課題テーブルから履修科目を自動抽出して未登録科目の設定を自動補完します。」
2. **第7回事後課題からの設計変更（重要）**:
   「第7回事後課題で検討した通り、当初の『単一の指定時刻』から、**『締切 24時間前・5時間前・1時間前』のように複数の事前タイミングを設定できる仕様**へ拡張しました。また、川邉さんのスケジューラとのデータ受け渡しを確実にするため、`notify_timings` カラムを **降順のカンマ区切り整数文字列（例：`"24,5,1"`）** に統一しました。」
3. **バリデーションと使いやすさ**:
   「`POST /settings` ではチェックボックスとカスタム時間（1〜168時間）を検証し、未選択や不正値の場合は詳細設計書通り『`通知時刻を正しく設定してください`』を表示して入力状態を保持します。HTML 上では科目削除フォームのネストを避けるため `form` 属性で分離し、仕様通りに安全に動作させています。」

#### コード説明の注目箇所
- プリセット（48, 24, 12, 5, 3, 2, 1時間前）＋自由入力、クイックボタン（「標準」「すべて解除」「全科目ON/OFF」）による検証しやすさ。
- `SettingController` で正規化保存し、`NotificationScheduler` で `.split(",")` する明確なインターフェース契約。

### D: 通知送信・通知履歴／再試行担当（川邉）

#### 発表台本（約1分）
1. **定期通知スケジューラ（`NotificationScheduler.java`）**:
   「私はバックグラウンドでの自動通知送信と、通知履歴・再試行機能を担当しました。`ManabaNotifierApplication` の `@EnableScheduling` により、`checkAndSendNotifications()` が60秒ごとに起動し、未提出かつ科目別設定が ON の課題を抽出します。」
2. **重複防止とエラー耐性**:
   「宮川さんの設定画面で保存された `notifyTimings`（例：`"24,5,1"`）をパースして締切 N 時間前のウィンドウに入ったかを判定し、`[5時間前]` のようなタグで `notification_logs` に `SUCCESS` が既に無いか確認することで、同じタイミングの重複通知を防ぎます。また、Web Push 送信でエラーが起きても課題単位で `try-catch` しているためスケジューラ自体は停止せず、`FAILED` として履歴に記録します。」
3. **通知履歴と再試行・リアルタイム受信（`HistoryController.java` / `history.html`）**:
   「`/history` では送信履歴を新しい順に表示し、`FAILED` の行には『再試行』ボタンを出します。再試行が失敗した場合は詳細設計書通りのエラーメッセージを表示します。さらに `history.html` が `/api/notifications/recent` をポーリングして実際のブラウザ通知ポップアップを出し、クリックで `/tasks` に遷移する流れまで実装しました。」

#### コード説明の注目箇所
- デモ用の `POST /history/trigger-check`（今すぐ通知チェック実行）と `POST /history/simulate-fail`（送信失敗ログ生成）により、授業内の限られた時間でも確実に自動通知と再試行を実演できる。

## 3. 設計変更・チーム連携の経緯まとめ（質疑応答対策）

| 質問想定 | 回答ポイント |
| :--- | :--- |
| **Q1. なぜ manaba を直接スクレイピングしないのか？** | 学内システムの認証方式・利用規約や HTML 構造変更の影響を受けやすいため。manaba が標準で送信する Gmail 通知メールを OAuth 2.0 経由で取得する疎結合な方式にすることで、安全性と保守性を高めた。 |
| **Q2. 第7回課題からどこを改善・詳細化したか？** | ① 通知時刻を単一時刻から「締切 N 時間前の複数選択（`24,5,1`）」へ拡張。② 機能C（設定保存）と機能D（スケジューラ判定）のデータ連携形式を降順カンマ区切り文字列に統一し、重複通知防止タグ（`[5時間前]` 等）の仕様を明確化した。 |
| **Q3. すでに提出済みの課題にも通知が飛んでしまわないか？** | 機能B で「提出済み」にすると `tasks.is_submitted = true` になり、機能D の `TaskRepository.findBySubmittedFalse()` の対象から即座に外れる。また機能A の Gmail 再同期でも既存の `submitted = true` を上書きしない設計としている。 |
| **Q4. 通知送信が失敗したときはどうなるのか？** | 例外をキャッチしてスケジューラ全体の停止を防ぎつつ `notification_logs` に `FAILED` を記録する。利用者は `/history` 画面からワンクリックで再試行（`POST /history/{logId}/retry`）でき、成功すれば `SUCCESS` に更新される。 |
| **Q5. 4人の開発をどのように衝突なく統合したか？** | 事前に `詳細設計書.docx` で共通テーブル（4 Entity）とセッションキー（`user_id`）を固定し、A（大友）が共通 Entity/Repository を提供、B・C・D が担当 Controller/HTML を並行実装する構成でコンフリクトを回避した。 |
